# SIMD

Date: 2026-11-11. Asked for by John: "we should implement all the four
core things suggested for the SIMD". The four are wider Array kernels,
more vectorized Array kernels, vectorizable user loops, and explicit
vector types.

## Step 1: wider kernels and new Array kernels

Design records: ADR-0085 and ADR-0086.

What works, on both backends:

- **Kernel dispatch.** On x86-64 every Array kernel is compiled for the
  baseline and for AVX2 (`crates/aura-runtime/src/array_simd.rs`,
  `widest`). The first Array operation of a process picks the copy.
  `AURA_ARRAY_KERNELS=baseline` keeps the baseline copies.
- **`--target-cpu`** on `aura build` and `aura run`, and
  `AURA_TARGET_CPU`: `generic`, `native`, and on x86-64 `x86-64-v2`,
  `x86-64-v3`, `x86-64-v4`. The name is part of the native cache key.
- **`fast_sum()` and `fast_mean()`** add over 32 partial sums in a fixed
  order, the same on every CPU.
- **`dot(other)`** over two Arrays of one shape. The float form adds in
  the reordered order. The integer form is checked.
- **`matmul(other)`** for `[n, k]` with `[k, m]` or `[k]`, and `[k]`
  with `[k, m]`. Each element adds its products in ascending inner
  index, so the result has the bits of the three-loop program.
- **Float `min` and `max`** compare 16 elements at a time and order
  `-0.0` below `0.0`.
- **`sum` and `mean`** no longer scan for a NaN before they add. The
  scan runs only when the result is NaN, to keep the canonical NaN.

Compiler developers: `AURA_DUMP_LLVM_IR=<prefix>` writes each unit's
optimized IR to `<prefix>.<unit>.ll`.

Measured in `benchmarks/simd` on the cloud container, `float64`,
milliseconds:

| Kernel | Aura | Rust | NumPy | Python |
| --- | ---: | ---: | ---: | ---: |
| `sum`, 1,024 elements, 400,000 times | 336 | 305 | 528 | 1,800 |
| `fast_sum`, same | 56 | 55 | | |
| `dot`, same | 120 | 297 | 299 | 19,000 |
| `min` and `max`, same | 196 | 718 | 1,084 | 7,500 |
| `matmul`, 64 by 64, 2,000 times | 108 | 150 | 26 | 42,400 |
| `matmul`, 512 by 512, 4 times | 100 | 232 | 10 | |

`sum` was 662 ms before the NaN scan went. NumPy is ahead on `matmul`
and on a large `dot`: its library fuses multiply and add, uses 512-bit
registers, and runs threads, and its result differs in the last digit.

## Step 2: counted loops over lists

No new language surface. Native code only: `aura run --backend mir` is
unchanged, and both backends give the same output and diagnostics.

- **Range proofs** (`native_codegen_range_loops.rs`). For a loop that
  reads a list's view once, the pass finds `int64` counters compared
  `counter < bound`, follows them through copies and constant offsets,
  and names the accesses that stay in range while two guards hold at the
  loop's entry: the counter starts high enough and the bound ends low
  enough.
- **Versioned copy.** The entry block checks the guards with the view.
  The copy drops the bounds check, the room check of a write, the sink
  test of a `mut` parameter, and the overflow check of the counter's
  advance. `mut` list parameters now get a copy too.
- **`element_address`.** Element addresses are a `getelementptr` from
  one pointer. Before, they were a sum of two words, which hid the stride
  from LLVM's loop vectorizer.
- **Branch weight.** The branch into the copy is weighted 2000 to 1, so the
  register allocator keeps the copy's values in registers.

Tests: eight unit tests of the proof, two backend tests, the
`counted_loops_over_scalar_lists` run fixture, three run-fail fixtures
for an index that leaves the list from inside such a loop, and a CLI test
that reads the optimized IR for a vector load.

Measured in `benchmarks/simd` (`loops.au`, `loops.rs`, `loops.py`),
milliseconds, 1,024 `float64` elements 400,000 times:

| Loop | Aura | Rust | Python |
| --- | ---: | ---: | ---: |
| `scale` | 58 | 62 | 22,800 |
| `saxpy` | 129 | 96 | 20,900 |
| `blur` | 297 | 291 | 45,700 |
| `clamp` | 355 | 349 | 21,100 |
| `dot` | 283 | 284 | 22,900 |

An earlier form of the same program took 2.23 s before this step and
0.7 s after. The rows move by a fifth between runs on the shared host.

Limits, stated in the manual: float reductions and checked integer
arithmetic stay scalar, a loop in a program that starts tasks polls for a
yield on every iteration, and `Array` element loops are not covered.
`range(a, b, step)` ran through a runtime range value at this point. Step
3 changes that.

## Step 3: lane values and stepped ranges

ADR-0087. The `simd` module is Aura source in
`crates/aura-compiler/std/simd.au`: `F64x2`, `F64x4`, `F32x4`, and
`F32x8` are Copy classes with one float field for each lane and methods
that compute lane by lane. The interpreter runs the methods as written,
so both backends agree on every bit by construction.

What native code needed to turn that into vector instructions:

- **Loads and stores as element accesses.** `mir_simd.rs` lowers a direct
  positional call of `load` or `store` on a local list as the constructor
  over `xs[i]`, `xs[i + 1]`, and so on, or as the element writes. The
  range proof of step 2 then guards every lane once at the loop's entry.
  A call it does not lower runs the method.
- **Inlined lane methods.** Each `simd` function that needs no frame is
  marked for inlining across codegen units. Float division, `abs`, and
  `sqrt` had kept a frame. `sqrt` is now `llvm.sqrt` and not a runtime
  call, in scalar code as well.
- **Stepped ranges.** `for i in range(0, len(xs) - 3, 4)` is the natural
  way to write a lane loop, and it took 105 s where the `while` form took
  0.09 s, because a step made a runtime `Range` value. A positive literal
  step now lowers as a counted loop. The advance happens only while the
  counter is at most `stop - step`, so it cannot overflow and the loop is
  exact at both limits of `int64`. Any other step, and a loop with
  `invariant` clauses, keeps the `Range` value.
- **The proof names counters by index.** A sum was exact when its place
  was known relative to a counter of a bounded name. Two tests of one
  counter against different bounds made that unsound, so the proof now
  keys on the counter test itself.
- **A stronger branch weight.** 16 to 1 on the branch into the versioned
  copy still left a lane accumulator on the stack. It is now 2000 to 1.

A trap inside a lane method that was called reports the file
`<std>/simd.au`. Without that, the report pointed at an unrelated line of
the user's file.

Tests: MIR lowering tests for the lowered and the called forms of `load`
and `store`, for a user class with a lane class's name, and for stepped
ranges with `continue`, a variable step, a negative step, and an
invariant. A backend test for the square root. Two range proof tests.
Fixtures `simd_lanes` and `for_range_stepped` (run-pass), three run-fail
fixtures for a load and a store past the list and a zero lane divisor,
and one check-fail fixture for the wrong element type. A CLI test builds
`examples/numbers/simd_lanes.au`, compares it with the interpreter, and
reads the optimized IR for vector multiplies and stores. The editor test
covers completion of the four classes.

Measured in `benchmarks/simd` (`lanes.au`, `lanes.rs`, `lanes.py`),
milliseconds, 1,024 elements 400,000 times. "Native" is a build for the
host CPU. Aura and Rust print the same checksums.

| Kernel | Lane class | Aura | Aura, native | Rust | Rust, native | Python |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `dot` | `F64x4` | 99 | 83 | 189 | 121 | 13,100 |
| `saxpy` | `F64x4` | 133 | 124 | 217 | 59 | 15,000 |
| `norms` | `F64x4` | 449 | 436 | 441 | 442 | 45,500 |
| `clamp` | `F64x4` | 169 | 87 | 149 | 61 | 29,600 |
| `absdiff` | `F32x8` | 105 | 56 | 280 | 23 | 17,000 |
| `sum8` | `F32x8` | 114 | 78 | 98 | 72 | 6,400 |

On a generic build Aura is at or ahead of the same lane structs in Rust.
On a host build Rust is about twice as fast on `saxpy`, `clamp`, and
`absdiff`, inside the three times bound. The scalar `dot` of step 2 takes
about 290 ms, so the `F64x4` form is three times as fast. Python is 60 to
300 times slower.

The lane classes were first declared without `copy`, because the parser
read `public copy class` as a constant named `copy`. A unit test caught
it. The parser now accepts the form, and the classes are Copy.

## Step 4: closing the host build gap

John asked on 2026-11-11 to close the gaps the step 3 table shows. On a
host build Rust was about twice as fast on `saxpy`, `clamp`, and
`absdiff`.

- **The stepped loop had two tests in each iteration**: `i <= last`
  before the advance and `i < stop` at the top. It now tests `i < stop`
  once and `i < last` after each body, with `last` equal to
  `stop - step`. A lane loop went from ten instructions for each
  iteration to seven.
- **The range proof follows two ways into the body.** A fact about an
  index now names where it comes from: the value at the loop's entry, or
  a test and the advances after it. An access is covered when every way
  can be guarded.
- **The entry keeps the strongest guard for each local.** An `F32x8`
  load asked for sixteen conditions, which LLVM compared in 512-bit
  registers. It now asks for two. The cost of a call on a 16-element
  list fell from about 33 ns to about 22 ns.
- **Telling LLVM that the advance cannot wrap made things worse.** The
  loop vectorizer then rewrote the stride loop with interleaved groups or
  gathers, and `saxpy` went from 113 ms to 225 ms. The hint is not
  emitted.
- **`F64x8` and `F32x16` were built and measured, and are not added.**
  They ran no faster than the four and eight lane classes on the AVX-512
  host, where LLVM keeps 256-bit registers.

Measured again, best of three:

| Kernel | Lane class | Aura | Aura, native | Rust | Rust, native |
| --- | --- | ---: | ---: | ---: | ---: |
| `dot` | `F64x4` | 80 | 66 | 145 | 132 |
| `saxpy` | `F64x4` | 94 | 91 | 215 | 62 |
| `norms` | `F64x4` | 442 | 444 | 434 | 441 |
| `clamp` | `F64x4` | 84 | 56 | 151 | 67 |
| `absdiff` | `F32x8` | 49 | 46 | 262 | 32 |
| `sum8` | `F32x8` | 95 | 84 | 93 | 77 |

What remains on the host build is `saxpy` and `absdiff` at about one and
a half times Rust. Rust's loop vectorizer widens the struct loop to
512-bit registers and unrolls it four times. About 9 ms of each Aura row
is the cost of entering the function 400,000 times.

## Step 5: integer lanes

The second gap was that the module had no integer lanes. ADR-0092 has
the decision.

- **`I64x2` and `I64x4`** come from the same generator as the float
  classes. They worked on both backends as soon as `simd_lane_count`
  knew their names, at about the speed of the scalar loop: each lane had
  its own overflow branch.
- **A prototype in Rust showed what one joined check buys**: an AVX2 sum
  in under half the time of the checked scalar loop. `native_codegen`
  now defers the overflow checks of a lane method to its return
  (`defers_lane_traps`, `flush_deferred_traps`), computes each as the
  sign of `(a ^ sum) & (b ^ sum)`, and tests the joined words once. The
  rare side repeats the checks in order, so the report is unchanged.
- **The joined form is used only on AVX2 targets** (`joins_lane_checks`).
  On the baseline it was twice as slow as the branches, because the rare
  side's use of each lane kept SLP from vectorizing.
- **`int32` lanes were built, measured, and removed.** `I32x8` products
  ran 0.8 to 1.1 times the speed of the scalar loop on every target. An
  `int32` is a 64-bit word with a range check, so the lanes took two
  registers and sixteen checks.
- **`min` and `max` on `int64` lanes stay scalar** below AVX-512.

Measured in `benchmarks/simd` (`int_lanes.*`), best of five,
milliseconds:

| Kernel | Aura lanes | Aura lanes, native | Aura plain loop | Rust lanes | Rust lanes, native | Rust plain loop |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `add` | 174 | 100 | 209 | 155 | 155 | 304 |
| `total` | 129 | 79 | 155 | 114 | 103 | 166 |

Tests: fixture `simd_integer_lanes` (run-pass) and three run-fail
fixtures for a sum, a difference, and a negation that overflow, a unit
test of `defers_lane_traps` that also emits both forms, a unit test of
the target rule, and on x86-64 a CLI test that builds the fixtures for
`x86-64-v3` and compares values, reports, and the vector IR.

Not measured: the joined check on AArch64. It keeps the branches there.

Not done, and stated in the manual: `int32` lanes, lane comparisons and
masks, a fused `mul_add`, and loads from an `Array`. A loop in a program
that starts tasks still polls for a yield in each iteration.

## Step 6: `matmul` in tiles and on threads (ADR-0093)

NumPy ran `matmul` four to ten times faster than the row kernel of
ADR-0086. Prototypes separated the causes before any change:

- **Exact AVX2 code is bounded at about half of NumPy's speed.** NumPy's
  library fuses each multiply with its add. The exact form needs two
  instructions and gives the three-loop program's digits.
- **A packed tile of 2 rows by 16 `float64` columns** with an inner
  block of 128 ran 1.7 to 1.9 times faster than the row kernel at 64,
  512, and 1,024.
- **512-bit tiles gave nothing** on this host, and tiles at the SSE2
  baseline were no faster than the row kernel.
- **A fused variant of the tiles** was only 1.25 to 1.35 times faster
  than the exact one, so no fused product is offered.

Implemented in `crates/aura-runtime/src/array_simd.rs`:

- `float_matmul` keeps its signature and picks a thread count from the
  work (`matmul_threads`: one thread for each 2^21 multiply-adds, at
  most `AURA_ARRAY_THREADS`, the CPU count, or 16).
- `float_matmul_on` splits whole rows over scoped threads and passes the
  kernel level to each.
- `float_matmul_rows` runs tiles at the AVX2 level and the row kernel
  elsewhere and for the columns after the last whole tile.

Measured with `benchmarks/simd/kernels.*`, best of five, milliseconds:

| Rows | Before | Now | Now, one thread | Now, baseline kernels | NumPy | NumPy, one thread | Rust loop |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 64 by 64, 2,000 times | 108 | 41 | 41 | 82 | 16 | 16 | 150 |
| 512 by 512, 4 times | 100 | 13 | 42 | 27 | 7 | 18 | 232 |

Tests: the frozen bit cases still pass, new sizes cross the tile and
block edges, one test compares the tiles with the row kernel on every
target, one compares one to seven threads bit for bit, and one covers
the thread rules.

Not done: NEON tiles (no arm64 host to measure), a fused product, and
threads for `dot` or the elementwise kernels, which are bound by memory.
